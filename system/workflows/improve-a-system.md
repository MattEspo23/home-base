# Improve a system

Use this workflow at session closeout, project closeout, opportunity review, or
when the user asks Home Base to improve a system.

## Suggestion budget

During ordinary work:

- offer at most one unsolicited suggestion per active session;
- record session, evidence, count, status, and next eligible revisit in
  `ideas/SUGGESTION-LOG.md`;
- save only a useful candidate;
- Treat “no” as durable.

An explicit opportunity review may show up to three ranked ideas and does not
consume this budget.

## Reopening a declined idea

Reopen only when new evidence changes a goal, tool, constraint, priority,
feasibility, cost, or risk. Explain the change and ask whether the user wants
to revisit. Home Base proposes materiality; the user decides.

## Two-run learning receipt

To prove a system improved:

1. save first-run input and result;
2. identify a specific problem or correction;
3. propose durable wording and obtain confirmation;
4. apply the smallest change;
5. run the same task again without asking the user to restate the correction;
6. compare the results;
7. record whether the intended improvement occurred.

Update the system’s `LEARNINGS.md` and `PROOF.md`. If the second run did not
improve, return the change to candidate status or roll it back. Do not call
saved storage “learning.”

## Complete the guided lifecycle

Set `you/SETUP.md` to `stage: complete` only when at least one system has:

- an observed result recorded in `PROOF.md`;
- a legible rollback or disconnect path;
- an explicit next action, including “use as-is and review later.”

A review, blueprint, or untested build alone is not completion. Completion
means the person has crossed from orientation into one proved, usable system;
Home Base can continue learning and expanding after that point.
