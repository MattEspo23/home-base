# Discover useful SOPs

Use this workflow when the user asks what to automate, document, delegate, standardize, or turn into a skill—or when they are unsure which repeated work is worth teaching Home Base.

## Make the idea plain

Do not assume the user knows workflow terminology. Explain an SOP only if needed:

> It is just a repeatable way you handle something, including the judgment calls and how you know it is done well.

Read the relevant parts of `you/`, `projects/INDEX.md`, `skills/INDEX.md`, and `tools/INDEX.md` first. Do not re-ask facts already confirmed.

## Interview one question at a time

Start from real work, not an abstract process inventory. Ask no more than five questions before summarizing:

1. “Think about the last week or month. What did you do more than once?”
2. “Which of those felt slow, annoying, easy to forget, or inconsistent?”
3. “Is there anything you often explain, hand off, or wish somebody else could do the same way?”
4. “Where do the information and tools for that work live today?”
5. “Which parts need your judgment or approval, and how do you know the result is good?”

Adapt to what the user already said. Accept “I don’t know” and partial examples.

## Build a small candidate set

Propose at most three candidates. For each, show:

- **Plain-language name**
- **Trigger:** what starts it
- **Useful outcome**
- **Why it may be valuable:** frequency, friction, consistency, delegation, or risk
- **What is known from a real example**
- **What is still unknown**
- **Approval boundary**

Recommend one candidate using the smallest useful scorecard:

| Signal | Question |
|---|---|
| Frequency | Does it happen often enough to reuse? |
| Friction | Would documenting it remove real effort or confusion? |
| Consistency | Would steps or checks prevent avoidable mistakes? |
| Leverage | Could the user or another person complete it faster next time? |
| Readiness | Is there a recent real example to learn from? |

Do not recommend automation merely because something repeats. Work with high judgment, high sensitivity, or no stable completion check may need a checklist or knowledge note instead of a skill.

## Confirm and route

Ask which candidate the user wants to improve first.

When they choose:

1. add or update one line under Candidates in `skills/INDEX.md` (it can stay
   unlinked until the skill file exists; then link it as described in Index
   entries in `system/WORKSPACE-CONTRACT.md`);
2. record only confirmed trigger, outcome, and approval boundaries;
3. route to `system/workflows/build-a-skill.md`;
4. begin with a recent real example.

If they are not ready, keep the ranked candidates in `inbox/LEARNING-CANDIDATES.md` as `unconfirmed`. Do not create finished skills from guesses.
